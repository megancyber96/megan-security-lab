Length and character checklist

Character types are observations, not requirements or proof of security. Longer, unpredictably chosen passwords matter more than adding a capital letter or symbol.

  • Missing: At least 12 characters
  • Missing: An uppercase letter (A–Z)
  • Missing: A lowercase letter (a–z)
  • Missing: A number (0–9)
  • Missing: A special character (such as !, @, or #)

Predictable pattern checks

  • Not checked: Contains a common password or obvious variation from this demo's list
  • Not checked: Contains a sequence of 4+ letters, numbers, or keyboard keys
  • Not checked: Contains a character 3+ times or a block of 2–128 characters twice in a row (ignoring case)
  • Not checked: Contains the word "password"

Educational estimate only, never a guarantee of security. Before pattern checks, lengths below 8, 12, 16, and 20 characters rate Very Weak, Weak, Medium, and Strong; 20+ rates Very Strong. Common-password matches or the word "password" reduce the rating to Very Weak. Detected sequences, repetitions, or fewer than five distinct characters (ignoring case) cap it at Weak. Capital letters and symbols earn no extra points. The small local list and simple checks miss many predictable choices and cannot identify reused or leaked passwords, measure entropy, or know how randomly you chose the input. Spaces count toward length, not as special characters.

Understand your result

Why length matters

Each extra randomly chosen character increases the number of possible combinations an attacker must try. Length helps most when the added characters or words are unpredictable; repeating the same letter adds little protection.

Why predictable patterns are dangerous

Attackers can try common words, number sequences, keyboard patterns, and repeated characters early. A long password built from these patterns can still be easy to guess, even with a capital letter or symbol added.

What is password entropy?

Entropy describes uncertainty in how a password is chosen. Imagine guessing a secret picked randomly from a bag: more equally likely choices make guessing harder. Random choices provide more uncertainty than familiar phrases or patterns. This meter is a checklist estimate; it does not calculate entropy or cracking time.

Why secure randomness matters

The browser's crypto.getRandomValues() produces random numbers designed to be unpredictable, using its cryptographic random number generator. We use those numbers to select characters. Math.random() is for everyday tasks such as games and animations; it is not designed to protect secrets.

A salt is NOT secret

A salt is a random extra value used when hashing a password. In a real system, it can be saved openly alongside the password hash. Different salts help keep identical passwords from producing identical stored hashes. They also make precomputed lists of password hashes less useful: the calculation must account for each salt.

Real password storage needs more

Salts do not make a weak password strong or make fast SHA-256 expensive to guess. Real applications need a dedicated password-hashing function or key derivation function (KDF), with a unique random salt and appropriate cost parameters. Prefer Argon2id; alternatives include scrypt, bcrypt for legacy systems, or PBKDF2 where required. Use a maintained library and tune its time and, where applicable, memory costs.

Try a one-character change

  1. Enter hello and generate its hash. Notice the result.
  2. Change only the first letter to make Hello, then generate again.
  3. Change it back to hello and generate again: the original hash returns.

A tiny input change produces a dramatically different-looking hash. This is the avalanche effect: on average, about half the output bits change. It does not mean every hexadecimal character must change.

Hashing is one-way, not encryption

SHA-256 creates a fixed-size, 256-bit fingerprint of your text. The same exact bytes always give the same fingerprint. A hash is not a hidden copy of the message, and there is no decryption key to recover it. One-way does not make predictable input secret: someone who already guesses the input can check its hash.

How encryption is different

Encryption protects a message so someone with the correct key can decrypt it and read the original. Hashing creates a fingerprint for comparison; it is not designed to recover the original message.

Why not store passwords with plain SHA-256?

SHA-256 is deliberately fast. Real password storage needs a dedicated password-hashing function such as Argon2id, configured to make guesses expensive. A unique random salt for each password makes identical passwords produce different stored hashes and prevents reuse of precomputed hash lists. The salt is stored alongside the hash and does not need to be secret. Adding a salt to plain SHA-256 alone is not enough.
